# 实测踩坑库

按「症状 → 根因 → 处置」组织。**开工前扫一遍能省掉大量返工。**

---

## 一、元数据口径类（错一次要全部重做）

### 1.1 分享方的集号 ≠ 元数据源的集号 → 必须按标题映射

**症状**：补齐后整季集号错位，海报与简介全是隔壁集的。

**根因**：资源分享方自己排了一套集号。实测偏差可达**几十位**，且不单调 ——
某季分享 `E06` 实际是元数据的 `E28`（差 22）；分享 `E17` 装的是 `E24` + `E25` 且**两段顺序相反**；分享 `E11` 装的是 `E31` 与 `E33`（`E32` 在别的文件里）。

**处置**：拿到资源先逐条把**文件名标题**与元数据标题归一化比对（`NFKC + 小写 + 去非字母数字`），建一张「分享编号 → 元数据集号」映射表。**只按编号对齐必然整体错位。**

### 1.2 元数据源自己会「串季」

**症状**：全季明明补齐了，客户端仍显示某几个集号是空的。

**根因**：元数据源把**下一季开头的几集同时挂在本季**。实测见过某季 50 条里有 4 条同时挂在下一季的 E01/E02/E04/E05 下。

**处置**：这是**数据源问题，不是漏补**。交付时讲明，并说明补下一季时会自然覆盖。

### 1.3 网盘/资源的「第 N 季」≠ 元数据源的季边界

**症状**：报出的缺口数量与另一种口径对不上；库里有集号在元数据源根本不存在。

**根因**：两套季划分不同。实测见过某剧 11 个季里 **8 个季的集数不相等**；两种口径下的缺口相差十几集。

**处置**：**先把逐季集数对照表摊给用户看，让用户选口径**，再动手。不要自作主张。越界集号（库里有、元数据源没有）是识别此问题的信号。

### 1.4 同一批短片可能挂在两个条目下

**症状**：以为有两笔缺口，其实是同一批内容。

**根因**：迷你剧/短片集的第二、三批常被元数据源**同时挂进母剧的特辑**。于是「母剧特辑缺 30 集」里一大半其实就是迷你剧的内容。

**处置**：报缺口时说明「这两批本质是同一种内容」，别让用户以为是两笔独立的活。

### 1.5 「命名合规」≠「刮削正确」

**症状**：文件名完全符合规范，客户端从某一集起整体错位一格。

**根因**：元数据源把两集并成了一集（或反之）。名字对，口径错。

**处置**：**先对齐口径，再谈改名。** 这是本 skill 的第一条铁律。

## 二、取数类（会让你「看不到全部文件」）

### 2.1 列表命令的命令行回显是「有界预览」，不是全量

**症状**：明明有 26 个文件的目录，回显只有 5 条 → 误判「文件丢了 / 没归位」。

**根因**：`--all` 的 stdout 是**有界预览**（实测封顶 5 条）。真实总数在 `result.data.total`，与回显条数不等**属正常**。

**处置**：**核实目录内容一律读落盘产物**（返回值里的文件路径），或让命令只输出摘要（`file_path` / `count` / `hasMore`），`count` 才可信。

### 2.2 目录 FID 必须传完整

**症状**：返回空结果，看起来像「目录是空的」。

**根因**：这类 FID 形如 `~1Xxx…|suffix`，**只给后半段会静默返回空**（不报错）。

**处置**：一律传完整 FID。沿用旧清单时特别注意。

### 2.3 FID 会因上下文变化 —— 任何命令回显的 FID 都不能直接拿来做后续操作

**症状 A**：上一轮记录里的 FID 拿到这一轮用，操作失败或找不到文件。
**症状 B**：用「新建目录」命令返回的 FID 去执行转存/移动，落位不对或失败。

**根因**：FID 形如 `<长串前缀>|<后缀>`。**后缀稳定，前缀会变**：
- 改名后前缀会变；
- 同一个目录，**新建命令的回显值**与**列表命令返回的值**，前缀也**不一样**（后缀相同）；
- 列表返回里，同一目录下**每个文件的 `parent_fid` 前缀也各不相同**。

**处置**：**任何命令回显里的 FID 都只当「本次调用成功」的凭证，不能当后续操作的输入**。
每轮开工前、每次写操作前，**重新列一次目录拿最新 FID**。这与「发布组发布名里的 FID 不能用」是同一件事。

### 2.4 「父目录」字段不能当分组键

**症状**：整理方案的操作项数量暴涨到「文件数 + 1」。

**根因**：列表返回里，**同一个目录下每个文件的 `parent_fid` 前缀各不相同**（后缀相同），不能用来分组。

**处置**：按**业务键**（季号 / 子目录名）分组；目标目录的 FID 要取自「列父目录」返回的**目录记录**，不能用文件记录里的 `parent_fid`。

### 2.5 分页上限

单页大小通常封顶 **100**，传更大值会报错。

## 三、整理/改名接口类

### 3.1 字符集校验比想象中严 —— 半角逗号和百分号也是非法的

**症状**：方案被拒，报「名称长度或字符不合法」。

**根因**：非法集包含 `\ : < > | * ? , / %`。**很多人只盯路径分隔符，漏掉 `,` 和 `%`。**
而且校验器是**抛出式，一次只报第一个错** —— 靠一遍遍试工具排查极其低效。

**处置**：
1. 本地先跑 `scripts/gen-rename-plan.mjs`（已内建同样的校验）。
2. 注意 **原文件名同样是校验对象**，而它**不能被改写** → 原名含非法字符时，需先单独做一次「预清洗改名」（普通改名接口的校验通常只查长度，能洗掉逗号）。
3. ⚠️ **元数据源里的官方作品名可能自带非法字符，不能照搬成文件名**：实测官方片名 `Thunderbolts*` 带 `*`，而 `*` 非法 ⇒ 建目录/命名时必须去掉。
   同类还有 `?`（如 `Where's Bingo?`）。**规范做法**：`*` 直接删、`?` 换成全角 `？`、`:` 换成 ` -`。

### 3.2 一个任务目录只绑一个冻结方案

**症状**：新方案 apply 报「冻结方案指纹不符」。

**根因**：上一轮 apply 成功后，该任务目录已冻结到上轮方案。

**处置**：**新一轮独立整理必须重新初始化**拿新任务目录。

### 3.3 check / apply 必须显式带任务目录参数

**症状**：整体失败，报「必填参数未提供」，容易被误判成「方案有问题」而反复改方案。

**根因**：工具**不会自动沿用最近一次初始化**。

**处置**：显式传参。

### 3.4 同一父目录下计划目录名不能重复；计划 id 不是目录 id

按字面处理即可。

### 3.5 遍历清单末行可能漏读

`while read` 处理无尾换行的清单时会漏最后一行。每轮单独补跑一次末尾项。

## 四、能力边界类（**别承诺做不到的事**）

### 4.1 网盘通常不提供「删除」能力

**实测**：命令表里没有 `delete`/`rm`/`trash`；接口清单只有 list / info / move / rename / upload / download / share；连「智能整理」收到「删除」指令也会**降级成移动/复制**。

**处置**：用户要删文件时，**用「移入隔离目录 → 用户在 App 手动删」的变通**，并明确告知：
- 隔离目录**不要放在季目录内部**（里面的文件仍带 `SxxExx`，会被当成重复集）；
- 文件删掉后**空目录同样删不掉**，需要用户一并手动删。

### 4.2 整理接口不负责清理空目录

搬空的旧目录会留成空壳，只能由用户手动删。**不要用「改名假装已处理」的变通。**

### 4.3 多集文件无法拆分

拆分 = 下载 → 切割 → 重传，成本极高。一般不拆，如实说明呈现差异（见 [naming-spec.md](naming-spec.md)）。

### 4.4 判「保留哪一个」要看分辨率，不看体积和容器

**实测**：同一集的两个版本，`.mkv` 是 1280×720 / 226 MB，`.mp4` 是 1920×1080 / 420 MB。
**`.mkv` 不代表更高清。** 用元数据里的宽高或清晰度档位比较。

## 五、资源侧类

### 5.1 「全圈性缺失」——换链接换不出完整版

**判据**（命中任一条即是）：
1. 多个不同来源的分享，**文件总数、目录名、层级完全一致** ⇒ 同源转存，不是独立采集；
2. 资源站标称的集数**明显大于**分享实有的集数。

**处置**：不要为了「有动作」而把重复文件转存进去（只会制造冗余）。如实交付「某部分完整、某部分全圈无源」，并给替代路径。

### 5.2 资源标题里的「第 N 季」可能是特辑拼盘

**实测**：某资源包的「第八季」只有 12 个文件，逐条核对后全是**特辑**（母剧特辑 4 + 衍生剧特辑 4 + 联动特辑 4），而真正的第八季一集都没有。

**处置**：**拿到分享先逐目录看文件条数**，与元数据源该季集数对照；条数对不上一律当「缺」。

### 5.3 目录名里的季号会骗人

**实测**：标「中文字幕版更新至第十三集」的目录，实际是**第 11 季的第 13 集**。

**处置**：**语言类别与季号都要钻进去看实际文件名**再确认。

### 5.4 一个分享里常并列多个语言版本

只认目录名不够，要按用户要求筛：采纳「原声 / 正式版带英文字幕」类，排除「配音 / 中文硬字幕」类。

### 5.5 失效分享有明确信号

「分享者已被封禁」「分享已取消」「文件不存在」「空分享」是四种不同的失败，逐个试并记录，别把失效当「没资源」。

**常见返回码**：`41011` 链接地址已失效 / `41012` 该链接已被用户取消分享 / `41031` 分享者已被封禁。
资源站的帖子里**大量链接是死链** —— 实测某次找一部片，8 个候选里 **5 个已失效**，只有 2 个存活。**永远准备 3 个以上候选**。

### 5.6 ⚠️ 「有杜比视界」≠「能看杜比视界」—— Profile 7 与 8.1 是两回事

**症状**：用户要 DV 版本，拿到「杜比视界」字样就交付；结果对方播放时画面**发灰、偏绿、颜色异常**，或压根只出 HDR10。

**根因**：DV 分 Profile，**播放兼容性天差地别**：

| | 蓝光原盘 REMUX | WEB-DL |
|---|---|---|
| 典型 Profile | **Profile 7（双层 / FEL）** | **Profile 8.1（单层 / BL+RPU）** |
| 兼容性 | **差** —— 多数播放器/电视只认基础层，退回 HDR10；部分设备颜色异常 | **好** —— 支持 DV 则出 DV，不支持**自动回退 HDR10**，几乎不翻车 |
| 画质/音轨 | 最高（无损原盘 + 无损音轨） | 有损音频、码率较低 |

**处置**：选源时**先问「拿什么设备播」**，再决定，不要只看「是不是 DV」：
- **Apple TV 4K + Infuse、支持 DV P7 的电视原生播放器** → 原盘 REMUX（P7）正确；
- **普通播放器 / 电脑 / 手机 / 老设备** → 选 WEB-DL（**P8.1**），否则可能颜色异常。

**同时给出两条路**（原盘 + WEB-DL），让用户按设备选，而不是替他赌一个。

### 5.7 判断规格要看发布名与元数据，不要只看资源站的宣传语

资源站的标题（如「4K 杜比视界 杜比全景声」）常是**转述**，实际可能对不上。可靠依据：
1. **原始发布名**（含 `2160p` / `REMUX` / `WEB-DL` / `DV` / `HDR` / 编码 / 音轨 / 发布组）；
2. **列表接口返回的元数据**（如 `video_max_resolution` 是否为 `4k`）；
3. 分享方在描述里标称的**字幕与配音语种**属于**未验证信息**，交付时要如实标注「分享方标注，未实测」。

## 六、验收类

### 6.1 「转存成功」不等于「补集完成」

转存默认落在**中转目录**，不是目标季目录。用户打开网盘看到的仍是文件堆在中转目录里。

**处置**：转存后必须再跑一次整理归位 + 改名，然后**回读两个方向**：目标季目录条数对得上、**中转目录 0 残留**。

### 6.2 别用「任务成功」当交付结论

报具体事实：目标季目录 26 项 / 命名 26/26 合规 / 中转目录 0 残留 / 可撤回窗口。
